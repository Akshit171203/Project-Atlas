==============================================================================
4. HALLUCINATION, AND THE MACHINERY THAT CATCHES IT
==============================================================================

    | Code: backend/app/services/answer_verifier.py,
    | backend/app/services/claim_extractor.py,
    | backend/app/services/citation_verifier.py, backend/app/services/nli.py,
    | backend/app/services/answer_repairer.py

WHY "JUST TELL IT TO USE ONLY THE SOURCES" ISN'T ENOUGH
=======================================================

The system prompt in backend/app/prompts/rag.py is unambiguous: use only the
provided sources, cite everything, never invent a citation, say so if the
sources don't cover it.

Models mostly comply. Mostly is the problem.

An LLM is trained to produce likely-looking text. When retrieved sources
almost answer a question, the highest-probability continuation is often a
smooth, complete-sounding answer that fills the gap with something from
training data, or with a reasonable-sounding inference the sources don't
actually license. Nothing in the model's objective distinguishes "I read this
in source 2" from "this is the kind of thing that's usually true."

And because the model isn't lying - it has no representation of the difference
- the hallucinated sentence looks exactly like the grounded ones. Same
fluency, same confidence, same citation format. You cannot spot it by reading,
unless you already know the answer, in which case you didn't need the system.

So the prompt is a request. Verification is a mechanism. This pipeline uses
both, and only the second one is checkable.

THE VERIFICATION LOOP
=====================

    answer text
       |  1. extract claims        (LLM call - decompose prose into atomic facts)
       v
    ["Arabica is mild and aromatic", "Robusta has more caffeine", ...]
       |  2. NLI-verify each claim (local model - free, no LLM call)
       v
    per-claim: entailment / neutral / contradiction + score
       |  3. if any unsupported -> repair (LLM call - rewrite without them)
       v
    repaired answer
       |  4. re-extract + re-verify
       v
    final verification result

Steps 2's cost profile is the reason this design is affordable: NLI runs on a
local cross-encoder, so checking every claim against every retrieved source
costs nothing but CPU. If verification were an LLM call per claim, the
exhaustive check in step 2 would be economically out of reach and the design
would have to be much stingier.

STEP 1: CLAIM EXTRACTION, AND WHY THE ANSWER GETS TAKEN APART
=============================================================

You can't verify a paragraph. Consider:

    | "Arabica is mild and aromatic, while robusta contains substantially more
    | caffeine and is easier to cultivate. [S1]"

Suppose robusta's caffeine content is in the sources and "easier to cultivate"
is not. Is that paragraph supported? There's no useful answer - part of it is,
part isn't, and a single verdict either passes a hallucination or flags a fact
that's perfectly fine.

So the answer is decomposed into atomic claims - one assertion each. The
prompt in backend/app/prompts/claim_extraction.py is explicit about this and
teaches by example, showing a compound sentence about the Maillard reaction
and caramelization split into two claims. That example is doing real work:
"one factual assertion" is not a self-evident instruction to a language model,
and the demonstration communicates the granularity better than the rule does.

Verification granularity is a design decision. Too coarse and you can't
localize a problem or repair it surgically. Too fine and you get fragments
with dangling pronouns that no source entails on its own. Sentence-ish atomic
claims are the workable middle.

  The failure mode that had to be handled defensively
  ---------------------------------------------------

Claim extraction asks the model to return JSON. Local models return JSON
wrapped in json fences, or with a preamble, or malformed. claim_extractor.py`
strips fences and, on a parse failure, returns an empty list rather than
raising.

That silent failure creates a trap, and it's handled in citation.py schema
[backend/app/schemas/citation.py]:

    if not self.verifications:
        return False   # NOT vacuously "all supported"

all([]) is True in Python. Without that guard, a claim extraction that failed
to parse would produce zero claims, zero claims would all trivially pass, and
an unverified answer would be reported as fully verified - the verification
layer failing open, silently, in exactly the way that matters most.

Fail closed. When a safety check cannot run, the correct result is "not
verified," never "nothing to object to."

STEP 2: NLI VERIFICATION, PER CLAIM, AGAINST EVERY SOURCE
=========================================================

For each claim, backend/app/services/citation_verifier.py:

  1. splits the source chunk into sentences
     (backend/app/services/source_sentence_splitter.py)
  2. runs NLI with each sentence as premise and the claim as hypothesis
  3. keeps the best entailment score across sentences
  4. marks the claim supported only if the label is entailment and the score ≥
     0.75

Why sentence-level premises rather than the whole chunk? NLI models are
trained on sentence pairs. Give one a 500-character premise and the supporting
evidence gets diluted by surrounding text the claim says nothing about,
dragging the judgment toward "neutral." Checking sentence by sentence and
keeping the maximum asks the precise question the model was trained to answer:
does this one sentence establish this one claim?

Why both a label and a threshold? The label comes from an argmax over three
softmax probabilities - entailment can win with 0.4 while neutral sits at
0.38. That's a coin flip presented as a verdict. Requiring 0.75 demands the
model be confident, not merely tipped. The threshold is the same kind of knob
as the evidence gate's, with an important difference: softmax outputs really
are probabilities in [0,1], so 0.75 has a natural reading ("75% confident")
that the reranker's -2.0 never had. Both are still empirical choices about
where you want the precision/recall trade to sit.

THE BUG: CITATIONS WERE MISATTRIBUTED, AND HONEST CLAIMS GOT FLAGGED
====================================================================

  The symptom
  -----------

Claims that were correct and fully supported by the retrieved material were
being marked unsupported, triggering unnecessary repairs.

  The cause
  ---------

Verification originally checked each claim against the source the LLM cited
for it. That assumes the model's citation is accurate.

It routinely isn't. A generating model reads five chunks, synthesizes across
them, and then attributes the whole synthesized statement to one citation
marker - usually the chunk it found most salient. A measured example: a claim
about Redis was cited [S1], but the sentence entailing it lived in [S2].

So the claim was true. The evidence was retrieved. The evidence was in the
prompt. The only thing wrong was the number in the brackets - and the
verifier, checking [S1] and finding nothing, reported a hallucination.

This is a false positive in a safety check, and false positives there are
expensive in a non-obvious way. They trigger repair calls that cost time and
money, and repair is instructed to remove claims it can't support - so a
correct, well-grounded fact gets deleted from the answer because the model put
the wrong number next to it. The verification layer was actively degrading
answers.

  The fix
  -------

backend/app/services/answer_verifier.py now checks each claim against every
retrieved source and keeps the best result:

    def _verify_against_all_sources(self, claim, registry):
        for source_id in sources:
            result = self.citation_verifier.verify(claim, source_id, registry)
            if best is None or result.score > best.score:
                best = result

The question changed from "does the source the model named support this?" to
"does anything the model was actually shown support this?" - which is the
question that matters. The system's promise is that answers are grounded in
the document, not that the LLM's bookkeeping is tidy.

It's affordable only because NLI is local and free: 5 claims × 5 sources × ~4
sentences is ~100 local forward passes, versus 100 API calls in a design where
verification cost money.

The general lesson: be precise about what your check is actually checking. "Is
this claim supported?" and "did the model cite correctly?" are different
questions with different failure consequences, and conflating them made a
citation-formatting quirk look like a hallucination. The trade-off is real and
worth naming - the system no longer detects misattribution, only
unsupportedness. That was the right call here, because a claim grounded in the
retrieved set is trustworthy regardless of which marker sits beside it, and
unsupported claims - the ones that actually harm a user - are still caught.

STEP 3: REPAIR, AND WHY A SECOND PASS HELPS
===========================================

When claims fail, backend/app/services/answer_repairer.py sends the answer
back with the source text and the list of failed claims, instructed to remove
or rewrite anything unsupported while preserving what was fine.

Why this works better than one more attempt at generating a good answer: the
second call has strictly more information. It has the sources, and the
original answer, and a specific list of what's wrong with it. Generation is
open-ended composition; repair is a bounded edit with the defects pointed out.
Narrow tasks get better results.

The repaired answer is then re-verified. It has to earn its way through the
same check - a repair that introduces a new unsupported claim doesn't get a
free pass.

  A prompt-engineering detail worth stealing
  ------------------------------------------

Rule 10 of the repair prompt spends four lines forbidding meta-commentary: no
"Note:", no "I removed...", no explanation of changes.

That rule exists because llama3.1 appended "Note: I removed the claims
about..." to a repaired answer. Two costs: the user sees editorial
housekeeping instead of an answer, and those tokens get billed on every
repair.

The general form: models default to being helpful about their process. If the
output goes straight to a user, you have to explicitly say so - and saying it
with examples of the forbidden phrasings works considerably better than saying
it abstractly.

WHERE VERIFICATION STILL FAILS - AND A DIAGNOSIS THAT TURNED OUT WRONG
======================================================================

Two eval cases, server_js_purpose and coffee_origins, are the two failures in
the current 8/11 end-to-end run that produce an answer. Both show the same
signature: ANSWER RELEVANT: True, CITATIONS SUPPORTED: False, REPAIRED: True.

The standing explanation in this project's notes was that both fail because
"the claims are true but phrased differently from the source text, so the NLI
check won't call them entailed" - paraphrase brittleness, the same root
problem as the reranker's in doc 2 [docs/02-retrieval-failures.txt]. One
explanation, two cases, and it matched a pattern already confirmed elsewhere
in the system.

It was tested by running the NLI model on the verbatim chunk sentences (read
from the database, not inferred from the eval's expected_answer field) and
then instrumenting the full query. It is wrong for both cases, and they turn
out to have nothing to do with each other. One is a verification bug. The
other is a chunking-and-retrieval bug that never reaches verification's real
limits at all.

  server_js_purpose: the premise's subject is a pronoun
  -----------------------------------------------------

The source chunk (chunk 162, document_id=10) reads:

    | "Back in server.js, this file acts as the orchestrator. It spins up the
    | HTTP server, connects to Redis, binds Socket.IO to the server, and
    | starts the background cron jobs."

citation_verifier.py splits that chunk into sentences and tests each one
separately as a premise. Measured on nli-deberta-v3-base:

    Hypothesis (identical in both cases):
        "server.js spins up the HTTP server."

    Premise A -- as citation_verifier.py actually sees it:
        ">>It<< spins up the HTTP server, connects to Redis, binds
         Socket.IO to the server, and starts the background cron jobs."

        label: neutral          entailment: 0.001

    Premise B -- same sentence, pronoun resolved:
        ">>server.js<< spins up the HTTP server, connects to Redis, binds
         Socket.IO to the server, and starts the background cron jobs."

        label: entailment       entailment: 0.998

One word - It -> server.js - moves entailment from 0.001 to 0.998.

The model is behaving correctly. Given only "It spins up the HTTP server,"
there is genuinely no way to know what It is. The premise, in isolation, does
not establish the claim. neutral is the right answer to the question that was
asked.

The bug is in the question we asked it. Sentence-splitting a chunk is what
makes NLI accurate (§ step 2 above - long premises dilute the signal), but
splitting also severs every anaphoric reference: pronouns and phrases like it,
this file, the plant, they, whose meaning lives in a previous sentence. Prose
is full of these - writers avoid repeating a subject in consecutive sentences
because it reads badly. So the sentences most likely to carry the substantive
detail are exactly the ones most likely to start with a pronoun.

The preceding sentence in that same chunk scores fine - "Back in server.js,
this file acts as the orchestrator." -> "server.js acts as the orchestrator."
is entailment at 0.847, because that sentence names its subject. So the claim
about what server.js is passes and the claims about what it does fail, purely
on grammar.

This is a real design bug, not a model limitation, and it's the more valuable
finding of the two. Candidate fixes, none implemented:

  - Sliding-window premises - test each sentence, and also each adjacent pair
    of sentences, keeping the best score. A pronoun's antecedent is almost
    always in the immediately preceding sentence, so pairs recover most of
    what splitting destroys at roughly double the local NLI cost (still free -
    it's a local model). Cheapest fix with the clearest mechanism.
  - Whole-chunk premise as a fallback - only when every sentence comes back
    neutral, retry with the full chunk. Accepts dilution as the price of
    context, and only on claims already headed for failure.
  - Coreference resolution at ingestion - rewrite pronouns to their
    antecedents before storing. Most thorough, most machinery, and it would
    help retrieval too.

  coffee_origins: not a verification failure at all
  -------------------------------------------------

The same test, on the verbatim source sentence:

    | "The plant is native to the highlands of Ethiopia, where local legend
    | credits a goatherd named Kaldi with discovering coffee's stimulating
    | effects."

-> "Coffee originated in the highlands of Ethiopia." = entailment at 0.997. It
passes comfortably, even though the premise says "The plant" and never names
coffee as the subject.

So NLI is fine here. Instrumenting the actual query (RAGResult already carries
everything needed) found the real chain, and it starts much earlier:

The chunk containing that sentence is never retrieved. The Ethiopia sentence
lives in chunk 43. Vector search's top 10 for "Where did coffee originate?" is
[53, 42, 51, 54, 44, 60, 45, 55, 65, 46] - chunk 43 is not in it, and isn't
for the rephrasing "Where did coffee come from originally?" either. Both of
its immediate neighbours, 42 and 44, are retrieved. The one chunk between
them, holding the answer, is not.

Why: chunk 43's text begins "romatic flavor, while robusta contains nearly
twice the caffeine and grows more easily at lower altitudes, making it cheaper
to cultivate..." - roughly its first half is about robusta's economics, and
the Ethiopia sentence sits in the middle. One 384-dimension vector has to
average all of that, and the average lands far from a question about origins
(doc 1 [docs/01-how-rag-works.txt], on what a single vector per chunk costs).

Meanwhile chunk 42 reranks first at +6.523 - because it contains the section
heading "1. The Coffee Plant and Its Origins." The word Origins is right
there. But 42's body is cut off at "while robusta contains nearly", before the
Ethiopia sentence. The heading that promises the answer and the text that
contains it ended up in different chunks, and the reranker took the heading.
That is the keyword-collision pattern from doc 2 [docs/02-retrieval-
failures.txt] reappearing on the easy document.

Given those five chunks, the model then did something quite reasonable:

    | "The exact origin of the coffee plant is not specified in the provided
    | sources, but it is mentioned that coffee cultivation spread across the
    | Red Sea to Yemen..."

That statement is true of the sources it was shown. The model didn't
hallucinate; it correctly reported a gap - a gap that only exists because
retrieval created it.

  And the claim that actually failed straddles a chunk boundary
  -------------------------------------------------------------

The claim that stayed unsupported through repair was:

    | "A French naval officer named Gabriel de Clieu carried a single seedling
    | across the Atlantic to the Caribbean island of Martinique in 1723."

neutral, entailment 0.003, against every source. It looks like a
hallucination. It is not - it's in the document, split down the middle:

  - chunk 53 ends: "...reportedly after a French naval officer named Gabriel
    de Clieu carried a single seedling across the Atlantic to"
  - chunk 54 begins: "carried a single seedling across the Atlantic to the
    Caribbean island of Martinique in 1723, nursing it through a difficult
    voyage..."

Chunk 53 says who. Chunk 54 says where and when. The LLM read both and
correctly combined them - that's synthesis working as intended. Verification
then tested the combined claim against each chunk individually, and neither
half entails the whole. Worse, chunk 54's first "sentence" has no subject at
all; it begins mid-sentence with a dangling verb phrase, which is the anaphora
problem above in its most extreme form.

Note what defeats what here. Checking every source rather than the cited one
(§ the misattribution fix) is exactly the right instinct, and it still loses
to this, because the evidence isn't in any single source - it's split across
two. Per-source verification cannot validate a claim synthesized across
sources, and synthesis across sources is a thing the generator is supposed to
do.

Then repair ran, and it made things stranger: it removed one failing claim,
added three new well-supported ones, and kept the unsupportable one - so the
case fails after a full repair round, having cost two extra LLM calls.

  What this case actually indicts
  -------------------------------

Not NLI, and not the LLM. In order:

  1. Chunking placed a section heading and its content in different chunks,
     and buried the answer sentence mid-chunk behind unrelated material.
  2. Chunking also split one factual sentence across a boundary, making the
     fact it states unverifiable by construction.
  3. Vector search couldn't surface a chunk whose average meaning is dominated
     by its majority topic.
  4. Verification has no way to validate a cross-chunk synthesis.
  5. Repair failed to remove a claim it could not support, despite being
     explicitly instructed to.

Chunking is upstream of everything, which is why doc 1 [docs/01-how-rag-
works.txt] calls it the decision that quietly limits the whole system.
Sentence-aware chunk boundaries and heading propagation would address 1, 2 and
3 at once - and none of the downstream fixes (better NLI, better reranker,
better prompts) touch any of them.

  The direction of these failures
  -------------------------------

Both are false negatives in a safety check: nothing false is served.
server_js_purpose flags a good claim because the premise lost its subject.
coffee_origins flags a real fact because the fact was cut in half at
ingestion. In both, the system errs toward refusing to vouch for something
true - never toward vouching for something false.

For a system built to be conservative that's the failure you'd choose. It
still isn't free: each costs two extra LLM calls for a repair round that
doesn't rescue the case, and together they are two of the three failures in
the current 8/11.

  And the methodological point, which is the reusable part
  --------------------------------------------------------

The original diagnosis was plausible, matched a real pattern confirmed
elsewhere in this project, and was wrong about both cases. Two failures got
one shared explanation because they looked identical from the outside - same
eval signature, same "true claim marked unsupported" shape.

A few minutes of running the models on the actual stored text split them into
two unrelated bugs with two unrelated fixes, and turned up a third thing
nobody was looking for (a fact severed by a chunk boundary). The cheap check
that would have caught this at any point was reading the chunk text instead of
reasoning about it - the same lesson as doc 2 [docs/02-retrieval-
failures.txt]'s problem 2, learned again in a different layer.

Identical symptoms are not evidence of a shared cause.
